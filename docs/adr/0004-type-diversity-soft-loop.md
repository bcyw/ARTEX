# 漏洞类型多样性用软回路调控，不加入库硬闸

ARTEX 的挖掘产出向越权/未授权滑移的根因不是提示词写了越权，而是越权是 LLM agent 证据门槛最低的「可证实」类型（双账号 A/B 交叉即满足危害最小证明物）。我们决定用 L1 提示词类型优先级重写 + L2 反馈回路（per-vulnclass 计数注入规划者上下文）软性调控，并给单一类型设每任务 2~3 个的同类上限；明确不采用「verifyGoal 硬匹配 vulnclass」（类型在该资产不可达成时目标永不关闭，任务卡死）和「SrcFindingBlocked 扩展成类型配额硬闸」（会把已证实的合法产出推进隔离区，与收取纪律「只看危害质量」的语义打架）。定级纪律不动：被留下的越权该 high 还是 high，挖掘偏好不扭曲验收口径。

类型词表同样不做硬编码：规范类型名与别名折叠表都住在 standards/src-acceptance.md 的挖掘方向节（启动读入、热改口径），Go 侧只做大小写/空白归一并读文件里的折叠表，代码中不出现任何漏洞类型字符串常量。上限数值、规范名、别名表全部免重编译可调。

## Considered Options

- L3 目标硬约束（verifyGoal 比对 goal.vulnclass）：拒绝，不可达目标会卡死任务。
- L4 入库硬闸（SrcFindingBlocked 扩展同类上限）：拒绝，把质量闸改造成产量闸会污染「收取纪律」的单一职责。
- 只改提示词（L1 单独）：拒绝，提示词约束会随上下文变长衰减，且规划者看不见自己的产出分布，无法自纠。
