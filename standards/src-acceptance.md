# SRC 漏洞收取标准

本文件是平台的漏洞产出质量纪律：**宁可少报，也不要数量**。只产出 SRC 平台可直接收取、有真实危害、可复现的漏洞。由启动时加载，注入到工具集含 `report_finding` 的角色（worker/planner/pentest/auto）的提示词（代码固定段）；黑名单同时作为入库硬闸。retester 走自己的提示词纪律（复测三态结论）。

## 一、总原则

1. **宁缺毋滥**：只报告有真实危害、SRC 平台大概率收取的漏洞。无把握时报 inferred 事实（record_fact），不报 finding。
2. **证据底线**：每条 finding 必须有「完整利用步骤 + 实际响应证据」。理论可利用、前置条件无法满足的，一律不报。
3. **黑名单一票否决**：命中黑名单类型且无升级证据的，不挖、不报；强行上报会被系统硬闸拦截进隔离区。

## 二、黑名单（默认禁止挖掘/上报）

| # | 类型 | 升级条件（满足才可报） |
|---|---|---|
| 1 | Self-XSS、无敏感操作的反射 XSS | 反射点位于鉴权/支付/个人资料等敏感页面上下文 |
| 2 | 低危 CSRF（改资料类） | CSRF 可触达敏感操作（改绑手机/邮箱、资金操作、管理操作） |
| 3 | JSONP 劫持、CRLF 无利用面 | 能实际带出敏感数据 / 完成可演示的危害 |
| 4 | 信息泄露（报错/目录列表/.git/备份）无进一步利用 | 从泄露内容实际还原出可利用物（如源码→拿到注入点/凭据） |
| 5 | 弱口令/默认口令 | 登录的是高权账户或可横向影响 |
| 6 | 理论 IDOR 无数据证明 | 展示了他人真实数据记录 |
| 7 | 未授权接口但返回无敏感数据 | 返回字段含手机号/订单/身份等业务敏感数据 |
| 8 | 端口/指纹/版本披露 | 无（一票否决） |
| 9 | 点击劫持、iframe 嵌套 | 无（一票否决） |
| 10 | 无回显/无利用链 SSRF | 拿到内网实际响应内容并可进一步操作 |
| 11 | 用户名枚举/账号存在性泄露（响应差异 oracle） | 从枚举实际走到接管（撞库成功登录他人账号）或批量泄露的用户清单本身即敏感数据 |

## 三、可收取类型的最低证据线（类型命门）

| 类型 | 命门（硬条件） |
|---|---|
| SQL/NoSQL/SSTI/XXE 注入 | 有确定输出或副作用证明，**最低共识 = 注出库名 database()**（盲注需时间差+库名内容）；仅报错关键词不算 |
| 越权/IDOR | **A/B 交叉证明**：A 的资源 B 的 token 能读/改，B 返回非空且等于 owner 视图内容；只读到自己不算 |
| 数据泄露 | 他人数据 + ≥3 敏感字段 + 非公开/非样例；自己测试账号数据 ≠ 漏洞 |
| SSRF | 服务端发出 + **回显内网数据**（云元数据/内网 banner/内网页面）；仅 DNSlog = 半成品不收 |
| 认证绕过/接管 | **任意**用户可绕过；OAuth/JWT/密码重置要 A/B 双账号证明 |
| RCE/命令执行 | 真实命令执行实证（能执行命令本身就是危害） |
| 业务逻辑/资金 | 操作真实生效且影响他人业务状态；自己测试数据不算 |
| 文件上传 | webshell 可执行或存储型 XSS 真实触发；纯存储不解析不成立 |
| 不成报 | 用户名枚举、CORS、安全头缺失、Cookie 标志位、单纯密钥/token 泄露（只作链证据） |

## 硬门（所有漏洞必过，缺一不报）

1. **先证伪**：假设"这是正常功能"，主动跑否定实验；证伪掉了 = 作废不报。
2. **PoC 可复现**：原始请求块直接粘贴可重放。
3. **危害是链路终局**：数据泄露/接管/资金/RCE/横向的终局结果，不是中间信号（枚举出用户名、拿到 token、摸清拓扑都不是终点）。
4. **服务端/权限边界确认**：不是浏览器 JS 假象/调试功能/渲染。

## 四、定级纪律

- **critical**：RCE、SQL 注入拖库、直接获取大量真实用户数据、核心账户接管。
- **high**：存储 XSS、成熟利用链的越权批量数据访问、支付逻辑漏洞。
- **medium**：单用户越权、反射 XSS（升级后）、需多条件串联的泄露。
- **low**：仅在前三类都不适用、但确实有真实危害时使用。
- 拿不准级别 → 降级不升级；实在拿不准 → 记 fact 交人工判断，不硬报。

## 五、复测纪律

- 复测结论 reproduced 才算有效佐证；连续 2 次复测无法复现 → 标记 false_positive。
- traffic_refs 中已含完整利用响应（proof 角色）的，视为已具备完整利用证据。
