# 中文 SRC 报告

正式报告面向安全评审，说明做成了什么、如何复核、影响及修复。遵守 [研究边界](security-research-context.md)；用户或 SRC 的报告模板优先。

## 一、正文格式

默认用以下字段。标题、目标 URL、等级各占一行；各大块用单独一行全角 `＃` 分隔，描述/危害标签后换行。文件名用漏洞标题的安全文件名形式，放任务 `报告/`，按接收方要求选择换行格式。

| 字段 | 内容 |
|---|---|
| 漏洞标题 | 目标 + 实际突破的权限/业务边界。匿名需有真正不携带有效凭证的复现；有会话跨对象称越权，不能只凭历史会话状态判断。 |
| 目标网站URL | 实际人可打开的入口；不包含凭证或敏感查询值。 |
| 漏洞等级 | 优先适用 SRC 定级标准；依据已证明影响、权限前提及利用条件。没有依据时说明暂定，不为提高等级追加高影响操作。 |
| 漏洞描述 | 以漏洞事实为主语，直接说明可复现的原身份、操作和实际结果；不写测试过程视角（不出现「我测了」「本趟」「复核」）。来源是 JS/文档时附来源路径；凭证/秘密按接收方标准（厂商 SRC 平台要求原文照贴时照贴）。 |
| 漏洞危害 | 区分已证明影响与条件性推断。举受控样例；可读权限不等于可写/可退款，未执行不编造成执行。 |
| 涉及接口清单 | 列实际复现涉及的完整路径、METHOD 与来源；敏感参数按接收方标准，不把首页或抄参文件冒充漏洞接口。 |
| 复现步骤 | 编号给出必要前提、基线、测试输入及实际结果。每步一个最小必要请求/命令，说明跨步骤变量来源；保留足够响应证据使评审能核实，不堆无关请求头。 |
| 修复建议 | 对准根因和共享检查点，给出可实施的校验/隔离方案及相关回归点。 |

请求中 Host 与请求行匹配；有 body 时注明实际 Content-Type。让客户端计算 Content-Length，避免手写失效长度。请求包给**最终形态**、审核者复制即发：无占位符（不出现 `***`、`<脱敏>`、`[REDACTED]`），body 为最终编码形态（不留需接收方二次解码的 `%20`），正文不写「详见证据/见前包」类跳转。凭证/秘密按接收方标准（厂商 SRC 平台要求原文照贴时照贴）；替换步骤说明在前提里。报告应能被接收方直接复制复现。

## 二、证据与收录

- 只有漏洞已确认（有可复现的请求/响应、payload 或等价证据，且能说明实际影响）才创建报告文件；未确认或仅理论可行的发现记入站点目录 `线索.md`，不产出正式报告。
- 命中工作区 `docs/exclusions.md` 的发现默认不写报告；用户明确要求完整审计时，可在报告中单列为「平台不收/待确认」，不冒充可提交漏洞。
- 确认的中危及以上 SRC 发现及时写报告；相同根因和接口增补原篇，不按换一个 ID 重复交。
- 默认不单独提交 CORS、仅缺安全头/版本/公开信息、未形成影响的上传下载、单纯 HTTP 200 等；用户要求完整审计时可单列低风险与待验证项，不隐瞒覆盖缺口。
- 疑似凭证泄露不等于凭证可用。仅在允许的服务与受控权限内做最小验证；不为证明泄露而转钱、读取大量数据或进入范围外系统。未验证时明确说明。
- 匿名、越权、可批量和执行能力各需对应证据；不能用一条成功响应推断无限权限。
- 报告按接收方标准（厂商 SRC 平台要求原文照贴时照贴）；知识库不包含秘密实值。复现所需的完整请求/响应原文**内嵌在报告里**（含 JS 完整 URL、grep 命中、页面→chunk→JS 定位三要素），正文不引用工作区内部文件路径；原始证据另行留在用户指定的受控位置。
- 清理只按 [目录规则](desktop-task-folder.md)，不由「有无报告」推导删除整个任务目录。
