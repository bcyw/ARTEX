# 查询机制研究：位置、语义与延迟消费

路线选择和停止条件见 [技术路线研究](../rules/technical-route-research.md)。从一次正常查询及其身份/租户开始，不要求“每个过滤参都测”。模板、表达式、脚本和外部命令消费者见 [解释执行](el-injection-test.md)，不混在 SQL payload 清单中。

## 定位输入与当前阶段

正例：自己的正常筛选、排序、报表或导出会改变服务端返回内容，已定位具体字段和结果观察面；或保存的规则在后续任务中被拼入查询。反例：只有搜索框、框架/数据库指纹、一次 500/超时、全文搜索正常匹配 `or`，以及只有登录墙且没有获准可达的查询。认证拒绝只说明本次身份到不了当前路径，不代表整类查询安全。

先记录身份/租户、正常请求、可控位置（query/body/header/path、JSON 值或键、保存字段）、正常返回的行/总数/排序/聚合、缓存和分页。区分接收与类型校验、查询构造、数据库/搜索执行、结果过滤、延迟导出；错误或内容变化归到有依据的阶段。

| 输入语法位置 | 最小对照与下一实验 | 竞争解释/反例 |
|---|---|---|
| 值：字符串、数字、日期等 | 固定其他条件，比较两个已知自有值；上下文或差分支持结构解释假设时，选符合该位置的一对有界条件 | 引号被当字面量、类型校验、转义/绑定与语法解释不同；单个引号报错不够 |
| 标识符：字段、列、集合、索引等 | 比较一个允许名称与一个无害不存在名称，结合白名单错误和可见字段变化 | 值参数化不能说明动态标识符安全；未知名称被拒也不证明整条查询可改 |
| 排序/投影 | 在自己的少量已知记录上改变合法方向/允许字段，确认差分位置；再围绕可疑表达式边界选一个对照 | 正常排序、UI 本地排序、默认回退、隐藏字段仍被结果层过滤，不等于越界 |
| 过滤表达式/查询片段 | 区分普通字符串、受限业务 DSL 与直接查询语法；使用语法已知且只约束自有记录的等价/反向条件 | 产品允许高级过滤本身正常；必须证明突破实际语法或数据边界 |
| 结构化对象/操作符 | 正常标量与一种类型/结构变化成对，观察是 schema 拒绝还是查询行为变化 | JSON 支持对象不等于操作符被执行；不同数据库的操作符不能互换 |
| 聚合、报表或延迟查询 | 用同一自有数据集、条件和版本比较最终产物，关联任务 ID 与执行时间 | 保存成功、任务排队、旧报表或最终结果过滤不能替代执行证据 |

405 先分清 HTTP 方法/路由拒绝、WAF 与业务参数错误；只有正常流量、源码或错误绑定信息支持时，才改到另一个输入位置。没有证据不把同一探针轮流塞进所有 header/path。

## 下一实验应区分什么

例如自己的列表正常能筛出两条，某条件返回更多：可能是查询逻辑被改，也可能是空值被解释为“不过滤”、全文搜索、分页计数口径、缓存或权限本就允许。先固定数据和分页，比较一个自有记录应命中的条件与应不命中的条件；必要时取一个受控第二身份对象的边界对照。不要直接使用全库恒真条件，也不把总数上升当成租户过滤已失效。

| 观察渠道 | 有界方法 | 反证/尚未支持的结论 |
|---|---|---|
| 内容、条数、排序、聚合 | 交错基线和单变量对照，尽量只看已知自有记录或最少结果；比较原始响应与业务归属 | `total` 变化、正常搜索命中、排序变化单独只证明行为差分；还缺查询结构或跨边界证据 |
| 错误 | 对照正常值、预期类型错误、结构相关错误，记录原始响应和任务阶段 | WAF/网关模板、统一 500、应用层校验不证明进入数据库；数据库语法错误也不等于能读敏感数据 |
| 时间 | 仅在存在条件执行假设且范围允许时，使用最小延迟、少量交错基线/真假条件，观察差异是否与条件稳定相关 | 网络抖动、重试、锁、队列、限流、缓存冷热和复杂查询都能变慢；一次慢请求不算。延迟不天然比内容差分安全 |
| 延迟结果 | 保存自己规则/报表并读回原始值 → 显式触发导出/任务 → 取本次产物；记录对象版本、任务、消费者身份、时间窗 | 保存过滤字段不等于查询已执行；“无结果”可能是任务未跑、重试或观察未完成 |

拿不到稳定观察面、区分不了噪声、语法/配置未知或无合法触发时，写具体 blocker。已满足真实危害证据就停止；无新增执行证据时按公共路线收束，不以遍历更多语法变体代替信息增量。

## SQL 与非 SQL 分支

- **SQL/HQL/类似查询语言**：先确认字符串值、数字值、标识符、排序表达式或完整片段的具体位置；参数绑定/白名单按位置判断。语法需符合实际方言和调用，不因 Java 就改用 SpEL。联合结果、错误或时间方法各自需要可达条件，不能从语法报错直接进入抽取或写操作。
- **文档数据库/结构化操作符**：关注服务器是否把用户对象/键合并成查询，是否限制操作符和字段；用自有数据上的最小结构差分验证。类型强制为字符串、键白名单或预期业务操作符是反例。Mongo 风格操作符不是所有 JSON 后端通用语法；不要把 `$where` 当作 ES DSL 的下一步，也不假定服务端脚本默认可用。
- **搜索 DSL/查询字符串**：区分全文关键字、查询字符串解析器、结构化 DSL 和实际 SQL 接口。允许布尔搜索/通配符可能就是功能；关注是否跨了既定租户/字段/索引或查询能力边界。搜索服务存在不证明应用把输入直接交给它。
- **XPath/LDAP/自定义规则等**：先从正常结构、源码或可归属错误确认语言与位置，再构造同一语义的正反对照；不能用 SQL 标点失败宣告安全，也不能在没有证据时各语言轮询。

源码辅助追踪“输入 → 类型/白名单 → 查询构造/绑定 → 执行 → 结果权限过滤”，同时核对连接身份与延迟消费者。代码拼接是重要假设，但实际是否可控、触发及跨界仍需目标证据。方言/API/特定版本行为另查对应一手文档；本篇不提供跨版本兼容矩阵。

## 业务案例：列表筛选项 OR + total

企业流水、消费、员工名单等列表可能同时返回 `rows` 与 `total`；保留这两个观察面，但**不从“有 total/后端是 ES”推定 SQL 注入**。

1. 用当前身份的正常筛选、一个不存在的自有值和少量已知记录建立基线，确认总数与分页含义。
2. 有查询位置/语言证据后，选择限制在自己的数据范围内、只改变一个逻辑条件的对照；观察差分是否与条件而非空值回退、文本匹配、缓存相关。
3. 总数异常只是机制线索。实际出现受控第二主体本不该可读的记录，或其他已证查询能力越界，才能支持对应危害；不为追求海量 `total` 放开全库条件。
4. 最小页大小并不能限制后端计数/排序成本。出现异常负载、超量结果或已有足够证据即停止，不翻页/导出补数量，不默认接 sqlmap dump。

旧案例中恒真 OR 可能放宽某段条件，也可能完全不影响独立租户过滤；不能断言一次 OR 必然去掉租户/日期。若 SQL 被当字符串，先确认实际 DSL/解析器，不能直接跳另一数据库的操作符。

## 业务案例：邮件订阅 iframe 同目录 list

旧案例是 iframe 订阅表单与列表接口共用租户参数，列表 `key` 同时参与鉴权和查询。只有现场页面/脚本/请求支持该接口关系时才沿同目录定位，外观相似不能证明固定 `list.php` 或拼接漏洞。

用自己的订阅测试记录与正常/错误 key 建基线；若存在拼接证据，再在明确租户和最少结果范围中比较语义对照。真正返回本不该读取的订阅正文才支持危害；固定 Wrong Key、空结果、常量比较、绑定参数、接口不存在分别收束当前假设。不得把一个历史皮肤扩展成同产品全网验证。

## 结论边界

仅改变自己的筛选结果、报错或计数不是自动 finding；报告类型与严重度仍由当前收取标准及已证实危害决定。查询执行、数据越界、修改成功、命令/模板执行是不同结论，跨机制时按证据转到对应指南，不把所有差分统称注入成功。
